# Agent Guide

This file follows [AGENTS.md](https://agents.md), an open, tool-agnostic
format for giving AI coding agents project context. It is read by agents
including OpenAI Codex, Cursor, Windsurf, Aider, GitHub Copilot, Google
Gemini CLI / Jules, Devin, Zed, and others. This repo does not ship a
`CLAUDE.md`, so a Claude Code session does not auto-load this file at
startup; read it yourself at the start of a session, or ask the user to
point you at it.

It captures the conventions that are not obvious from a single file, so an
agent can make a correct change on the first try instead of re-deriving the
architecture from scratch.

Read this before making changes. If something here turns out to be wrong or
stale, fix it as part of your change.

## What this project is

A Go boilerplate for building REST APIs with Gin. It wires together:

- Dependency injection: [fx](https://github.com/uber-go/fx)
- HTTP routing: [gin](https://gin-gonic.com)
- ORM: [gorm](https://gorm.io/docs) against MySQL
- Logging: [zap](https://github.com/uber-go/zap)
- API docs: [gin-swagger](https://github.com/swaggo/gin-swagger) / [swag](https://github.com/swaggo/swag)
- Migrations: [atlas](https://atlasgo.io/)
- Hot reload: [air](https://github.com/air-verse/air)

Module path: `boilerplate-api` (see `go.mod`). Go version: 1.23.

## Repository layout

| Path            | Purpose                                                                 |
|-----------------|--------------------------------------------------------------------------|
| `api/`          | HTTP feature modules, grouped by area (`admin/`, `auth/`, `user/`, `utility/`, `swagger/`). |
| `lib/`          | Shared infrastructure: `config`, `middlewares`, `router`, `api_errors`, `json_response`, `auth`, `idempotency`, `request_validator`, `types`, `utils`, `constants`. |
| `database/`     | `dao/` (generated, do not hand-edit), `migration/` (Atlas migrations), `seeds/`, `schema.sql`. |
| `services/`     | External integrations: AWS, GCP, Firebase contract, Stripe, Twilio.     |
| `cli/`          | Interactive CLI commands, entered when the binary is run with `cli` as `os.Args[1]` (see `lib/utils/isCli.go`). |
| `bootstrap/`    | The fx wiring root and the HTTP server lifecycle (start, migrate, seed, shutdown). |
| `automate/`     | The `make crud` scaffolding script and its templates, plus `make link-skills` (`automate/scripts/link-agent-skills.sh`). |
| `docker/`       | Dockerfiles and compose support files.                                 |
| `swagger/`      | Generated by `swag init` (`docs.go`, `swagger.json`, `swagger.yaml`). Do not hand-edit. |
| `__mocks/`      | Shared package-level fakes/fixtures used across tests.                 |

## The feature module pattern

Every feature package (for example `api/user/user`) follows the same shape:

- `model.go`, `dto.go`: gorm models and request/response DTOs.
- `repository.go`: an `IRepository` interface plus a `Repository` struct that talks to `config.Database`.
- `service.go`: an `IService` interface plus a `Service` struct holding the business logic, depending on `IRepository`.
- `controller.go`: a `Controller` struct with gin handlers and `@swag` annotations.
- `route.go`: `SetupRoutes(...)` registers routes on the shared `router.Router`.
- `module.go`: an `fx.Module` that wires `Repository -> Service -> Controller` and invokes `SetupRoutes`, exposing the repository and service as interfaces:

```go
fx.Provide(
    fx.Annotate(NewRepository, fx.As(new(IRepository))),
    fx.Annotate(NewService, fx.As(new(IService))),
    NewController,
),
fx.Invoke(SetupRoutes),
```

Interfaces exist so a `Service` can be unit-tested against a hand-written mock
of `IRepository` (see `api/admin/user/repository_mock.go` and
`api/admin/user/service_test.go`) without touching a real database. Follow
this pattern for new code: depend on the interface, not the concrete struct.

A new module gets registered in its parent `module.go` (for example
`api/admin/module.go` or `api/module.go`), the same way the existing ones
are.

## Adding a new resource

Claude Code users: the `scaffolding-crud-resources` skill runs this as a
guided checklist.

1. Run `make crud`, which runs `automate/scripts/crud.sh` and asks for a
   target folder (for example `api/product/product`). It scaffolds
   `repository.go`, `service.go`, `controller.go`, `routes.go`, and
   `modules.go` from `automate/automate-templates/*.txt`.
2. Fill in the interface methods, GORM model, and DTOs.
3. Add real routes in `routes.go` and swag annotations on each controller
   method (see the pattern in `api/user/user/controller.go` and
   `SWAGGER.md`).
4. Register the new `fx.Module` in the parent module (for example add it to
   the `fx.Options(...)` list in `api/module.go` or the relevant area's
   `module.go`).
5. If the resource needs a table, write an Atlas migration (see
   `database/migration/`) and regenerate DAO structs with `make dao`.
6. Run `make swagger` so the generated docs match the new/changed
   annotations.

## Commands

| Command               | What it does                                                              |
|-----------------------|-----------------------------------------------------------------------------|
| `make run`            | Starts the hot-reload dev server via `air` (installs `air` if missing).    |
| `make migrate`        | Runs `atlas migrate apply` (local host if `env=local`, otherwise inside the `web` container). |
| `make schema`         | Runs `atlas schema apply`/diff.                                            |
| `make dao`            | Regenerates `database/dao/*.gen.go` from the live DB schema via `gentool`. Never hand-edit those files; change the schema and regenerate instead. |
| `make swagger`        | Runs `swag fmt` and `swag init`, regenerating `swagger/docs.go`, `swagger.json`, `swagger.yaml`. Never hand-edit those files. |
| `make crud`           | Scaffolds a new resource folder (see above).                               |
| `make link-skills`    | (Re)creates the `.claude/skills` and `.codex/skills` symlinks pointing at `.agents/skills`. Safe to re-run any time, e.g. after a fresh clone or if a symlink goes missing. Pass extra agent names to link more, e.g. `make link-skills cursor .windsurf`. |
| `make install`        | Installs a pinned `golangci-lint` and points git's `core.hooksPath` at `hooks/`. |
| `go build main.go` / `go run .` | Builds/runs the HTTP server.                                     |
| `go run . cli`        | Runs the interactive CLI instead of the HTTP server.                       |
| `go test ./...`       | Runs all tests.                                                            |
| `golangci-lint run`   | Lints the repo (the pre-commit hook runs `golangci-lint run --fast`).      |

## Conventions to follow

- **Errors**: build errors with `lib/api_errors` (`HttpErrorType` constants and
  `ErrorResponse`), and let `lib/middlewares/error_handler.go` render the
  response envelope, which includes the `trace_id` set by
  `lib/middlewares/request_id.go`. Do not build ad hoc `gin.H` error bodies in
  new controllers.
- **Responses**: use the generics in `lib/json_response`
  (`Data[T]`, `DataCount[T]`, `Error[T]`, `Errors[T]`, `Message`) so response
  shapes and generated swagger schemas stay consistent.
- **Receiver names**: every method on a given struct must use the same
  receiver name (this is checked in PR review, see
  `.github/workflows/pr_guidelines.yml`). Pick one short name per struct
  (`c`, `cc`, `s`, ...) and use it on every method of that struct.
- **Swagger annotations**: every exported controller method needs
  `@Tags`/`@Summary`/`@Description`/`@Security`/`@Produce`/`@Success`/`@Failure`/`@Router`/`@Id`
  comments, following `api/user/user/controller.go`. Use distinct `@Tags`
  values for user-facing vs admin-facing endpoints (see `SWAGGER.md`). Mark
  required DTO fields with `validate:"required"` so the generated client
  types are non-optional (see `SWAGGER.md`). Run `make swagger` after
  touching any annotation or DTO.
- **Config**: every env var goes through the `Env` struct in
  `lib/config/env.go` (`mapstructure` tag) and must also be documented in
  `.env.example`, which is the source of truth for local setup. Add
  `validate` tags for required values. Claude Code users: the
  `adding-environment-variables` skill runs this as a guided checklist.
- **Migrations**: write Atlas migrations under `database/migration/`, then
  regenerate `database/dao/` with `make dao`. Never hand-edit generated DAO
  files or the migration checksum file (`atlas.sum`). Claude Code users: the
  `creating-database-migrations` skill runs this as a guided checklist.
- **Commit messages**: this repo uses Conventional Commits
  (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `migrate:`), imperative
  mood, lower-case type prefix. Match the style in `git log`.
- **Docs style**: do not use em dashes in new documentation files (this one
  included). Use a comma, period, colon, or parentheses instead. This is a
  style rule for new content, not a mandate to reformat existing docs.

## Middleware order

Defined in `lib/router/router.go`, and the order matters:

`RequestID -> CORS -> ErrorHandler -> Idempotency -> Sentry`

`RequestID` must run first so the request id is available for error
envelopes and Sentry events. `Idempotency` is mounted globally and
self-gates: it only does work for `POST` requests carrying an
`Idempotency-Key` header, so it is safe to leave mounted globally.

## Testing

- Unit tests live next to the code they test (`service_test.go`,
  `store_test.go`, `time_test.go`, `firebase_test.go`, ...).
- Mocks are hand-written structs that satisfy an `IRepository`/`IService`
  interface with overridable `*Fn` fields (see
  `api/admin/user/repository_mock.go`). Keep a mock next to the interface it
  implements so they stay in sync.
- DB-touching code is tested against `go-sqlmock`, not a real database.
- Run a single package's tests with `go test ./api/admin/user/...`.

## CI

CircleCI (`.circleci/config.yml`) builds the binary against a real MySQL
service container, starts it, and curls `/health-check`. Keep that endpoint
working without requiring anything beyond a DB connection.

## Before you finish a change

Claude Code users: the `verifying-changes-before-commit` skill runs this as
a guided checklist.

1. `golangci-lint run` (or `--fast` to match the pre-commit hook) and
   `gofmt`/`go vet` clean.
2. `go build ./...` succeeds.
3. `go test ./...` passes for any package you touched.
4. If you changed controller swagger comments or DTOs, run `make swagger`.
5. If you changed the DB schema, add a migration and run `make dao`.
6. If you changed documented, user-facing behavior, update `README.md` or
   `SWAGGER.md` to match.
